提完PR就去做别的事，然后开始等——等CI跑完、等代码审查意见回来、等你去改bug、等合并冲突解决，最后再找人来点那个批准按钮。这条路 Anthropic 想用三个 AI 智能体帮你走完。

## 卡在 PR 里的那些事

### 为什么这段流程成了 AI 写代码时代的瓶颈

Anthropic 官方给出的数据是：Claude Code 团队在 2026 年 6 月到 9 月之间，合并的 PR 数量翻了一倍，回滚比例下降了 40% 以上。

更让人在意的是另一个现象。团队里大部分代码已经由 Claude 生成，写代码的时间压缩到几分钟，但 PR 从打开到合上的周期并没有同比缩短。

瓶颈不在写代码。

在真实项目里，这段流程的摩擦点有三个：CI 失败后要排查原因重新跑、合并冲突要手工解决、人工 review 的意见轮次多而且周期长。

写代码的速度上去了，等 PR 的速度没跟上，于是「AI 写代码只要几分钟，等 PR 的人却能卡你一周」就成了普遍体验。

### 三个智能体各管一步：审、修、批

Claude Ship 的设计思路是把这三步拆开，让不同的 Agent 负责不同环节。

Code Review 负责找问题。它不是简单扫一遍 diff，而是结合仓库里相关的上下文代码一起读，然后把发现的问题按严重程度排序，挂到具体的代码行上。团队可以选择 Quick、Standard 或 Deep 三种审查深度。

PR Steward 负责修问题。它处理三类事情：CI 检查失败、合并冲突、以及 Code Review 或其他审查者留下的意见。每次它推一个修复 commit，都会在 PR 评论里说明自己改了什么，以及如果需要撤销该怎么操作。它没有批准或合并的权限，分支保护规则依然生效。

Claude Approvals 负责批。它的工作方式是读取团队写在仓库里的审批策略文件——这个文件可以用自然语言编写——然后综合 Code Review 的结果、CI 状态、以及团队自定义的分类器信号，判断这个 PR 是否达到了合并条件。

> Claude Ship PR 流转架构



### 一个仓库里的实际流转顺序

在 GitHub 上的实际工作流是这样的：PR 打开后，Code Review 先介入，给出问题列表；PR Steward 收到反馈后自动处理 CI 失败和冲突；最终到达 Claude Approvals 时，如果策略文件认定这是一个低风险变更，就直接批准，否则转交人工。

整个过程里，开发者只需要关注最终结果，不需要反复切换上下文去手动推动每一步。

## 取舍与边界

### Beta 阶段的已知局限

官方文档里写得比较清楚：Claude Ship 仍处于 beta 阶段，至少有三条限制要留意。

一是它不能保证完全覆盖所有场景。AI 可能会漏掉某些边界条件，特别是在安全性要求高的仓库里，误报和漏报都可能出现。

二是支出需要控制。官方建议团队先设置每月支出上限，然后在观察模式下运行，不要一开始就让它全自动批准合并。

三是对策略文件的质量有依赖。Claude Approvals 的判断效果直接受团队写的审批策略影响，策略写得模糊，它也会含糊。

### 哪些团队适合先用

从现有测试数据和设计逻辑来看，这类团队更适合优先尝试：

第一，代码主要由 AI 生成的团队。你们写代码快，但等 PR 的周期长，Claude Ship 正好补上这段缺口。

第二，已有清晰审批策略的团队。策略文件写得越具体、越可执行，Claude Approvals 的准确率越高。

第三，愿意先在单个仓库里灰度使用的团队。不要一次性在所有仓库开启，先用一个中等复杂度的项目试水。

一个常见的错误是直接让 Claude Approvals 拥有合并权限而不设边界。这种做法的风险在于，一旦策略文件出现漏洞，AI 可能批准一些本应被拦截的变更。

更稳妥的做法是：先在观察模式下运行 Claude Approvals，让它输出判断但不实际执行，对比它的决策和人工决策的差异，确认一致后再逐步放开权限。

## 可执行的判断

Claude Ship 的价值在于替代人工审查里那些重复、机械、耗时但风险可控的环节。

如果你的团队已经习惯用 Claude Code 写代码，且正在被 PR 的等待周期折磨，那么现在值得做的是：选一个非核心的仓库，开启 Code Review 和 PR Steward，先观察一段时间，再决定是否启用 Claude Approvals 的自动批准能力。

如果你的仓库涉及核心业务逻辑，或者团队还没有建立清晰的审批策略文件，那先在观察模式下看它怎么审、怎么修，比直接上线更稳妥。

更狠的是，这套工具让 AI 写代码的真正闭环终于完成——写代码只是第一步，把代码顺利推到主分支才是第二步。Anthropic 这一步，踩在了大多数人还没意识到的痛点上。

## Claude Ship 怎么用

Claude Ship 发布于 2026 年 11 月 23 日，面向 Claude Team 和 Enterprise 用户开放。

三个智能体各管一步：Code Review 负责找问题，PR Steward 负责修问题，Claude Approvals 负责批 PR。

### Code Review：怎么找问题、找多深

Code Review 的功能已经正式开放。它会读取变更内容，并结合周围代码库上下文进行审查。

发现的问题以行内评论的形式贴在对应代码行上，并按严重程度排序。

搜索范围可以选择 Quick、Standard、Deep 三种深度。Quick 模式只扫当前改动涉及的代码，Standard 会看相关依赖，Deep 则会把整个相关文件都读进去。

Anthropic 官方称，团队内部 6 月至 9 月使用 Code Review 后，合并 PR 量翻了一倍，回滚比例下降了超过 40%。

### PR Steward：能帮你改什么、不碰什么

PR Steward 处理三类事务：CI 检查失败、合并冲突、以及审查意见反馈。

每次推送修复后，它会在评论里说明自己改了哪里、怎么撤销。

它的定位是辅助修 bug，不会批准或合并 PR。最终合不合并还是走你原来的分支保护规则。

### Claude Approvals：策略怎么写、哪些能动哪些不动

这是最复杂的一环。

Claude Approvals 不直接做决定。它读取仓库里的审批策略文件，按策略文件里写的内容判断该不该批。

策略文件用自然语言写。可以指定哪些改动可以自动通过，哪些改动必须人工审查。

Approvals 在决策时会综合多种信号：Code Review 的检查结果、企业自建分类器的输出，以及其他团队接入的信号。

## 真实数据是什么

### 官方说的 6→9 月合并量翻倍、回滚降 40%

Anthropic 公布的数字是：Claude Code 团队在 6 月到 9 月之间，合并的 PR 数量翻了一倍以上，回滚比例下降了 40%。

这个数字来自公司内部数据，没有经过第三方审计。官方口径是「内测数据」，适用范围是 Claude Code 团队的内部仓库，不是公开 benchmark。

更准确地说，这些数据反映的是 Claude Ship 工具在他们自己团队里的表现，不是通用基准。任何工具在自家团队里跑出来的数字，都应该带着这个前提看。

### 测试期的限制和风险点

Anthropic 明确说这三件套目前只有一部分是 GA（Code Review），PR Steward 和 Claude Approvals 还在 beta。

工具还在迭代，边界条件可能没覆盖完全。

官方给的建议是三点：

第一，先用观察模式跑一段时间，让 Claude Approvals 只输出判断结果，不实际执行审批。

第二，先在单个仓库里启用，不要一次性全仓铺开。

第三，设置每月支出上限，防止 Agent 跑飞导致费用失控。

这里有一个容易忽视的细节：Claude Approvals 的审批决策依赖你写的策略文件。策略写得模糊，结果就不可控。

另一个风险点是误判。Anthropic 在文档里直接写了：「Claude 使用 AI，可能会遗漏 bug、安全漏洞或其他问题。」这不是客套话，是明确的免责声明。

工具能帮你加速，但不能替你兜底。如果团队对代码质量有硬性要求，人工复核那一步不能省。

## 这套东西到底靠不靠谱

### 官方数据背后的前提条件

回到之前的数字：合并量翻倍、回滚降 40%。

这些数字的前提条件是：Claude Code 团队自己用的工具，在自己团队的仓库里跑的。

换个角度看，这组数据至少说明一件事：当代码主要是 AI 生成的时候，PR 流程的瓶颈会转移。写代码变快了，但审代码、修代码、批代码的速度没跟上。

Claude Ship 解决的正是这个新瓶颈。

### 谁该先用、谁不该碰

适合先试的团队：

- 代码主要是 AI 生成的，或者 AI 参与度很高
- 团队有成熟的分支保护策略，不会因为 AI 审批而降低门槛
- 愿意先在单个仓库里灰度，观察一段时间再扩大范围

不适合立刻上的场景：

- 对合规要求极高的行业（金融、医疗等），需要完整的人工审计链
- 团队没有成熟的代码审查文化，指望 AI 替代审查
- 不愿意为可能的额外费用设置上限

坦白讲，这套工具目前更适合内部实验，不适合直接当成生产环境的默认流程。官方自己也是这个态度。

## 下一步该做什么

如果你正在考虑要不要用 Claude Ship，今天的动作可以有三件：

第一，去 Claude Code 的设置页面打开观察模式，让 Approvals 只输出判断，不执行。

第二，在你的一个非核心仓库里配策略文件，跑一周看看结果。

第三，如果观察期的判断和团队人工判断的结果差异很大，停下来重新审视策略，而不是强行上线。

AI 写代码只要几分钟，等 PR 的人却能卡你一周。Anthropic 想解决的是这个摩擦，但工具还在成长期。先用观察模式验证判断的一致性，再决定是否把审批权交给它。

过去一年，Claude Code 团队内部绝大部分代码由 Claude 撰写。Boris Cherny 在官方博客写道：「一年前我们发布了 Opus 4.5，它是第一个替我写了 100% 代码的模型。但 PR 的交付一直没有跟上。」Claude Ship 就是为了解决这个最后一公里问题。

## 现在能上手吗

### 谁能用、怎么启用、观察模式为什么重要

Claude Ship 面向 Claude Team 和 Enterprise 计划用户开放。从 2026 年 11 月 23 日起，用户可在 GitHub 仓库中启用。

启用方式很直接：进入 Claude Code 设置页面，选择要启用的仓库，打开 Code Review 和 PR Steward。Claude Approvals 则在仓库放好策略文件之后才生效。或者在本地仓库的 Claude Code 命令行中输入 `/ship` 命令，即可对当前 PR 触发完整审查流程。

但官方建议先不要全开。Anthropic 明确推荐「观察模式」——Claude Approvals 会给出审批判断，但不实际执行合并。开发者可以看到 AI 会怎么批、为什么不批，而不必承担误批准的风险。

观察模式的价值在于建立信任基线。你不需要立刻相信 AI 的判断，只需要确认它的判断和你的判断大致同向。如果发现 Claude Approvals 频繁批准你认为有风险的改动，说明策略文件需要调整，或者团队规范本身存在模糊地带。

### 支出上限和分支保护规则的作用

Claude Approvals 的审批决策、PR Steward 的修复推送，都会消耗模型调用。对高频提交的大型仓库，月度支出可能超出预期。官方建议为每个仓库设置每月支出上限，防止 Agent 费用失控。

官方提供的控制手段有两个：支出上限和分支保护规则。支出上限管成本，分支保护规则管合并权限，两者构成这套流程的兜底。

分支保护规则是 GitHub 原生功能与 Claude Ship 的配合点。PR Steward 明确被设计为「不批准、不合并」的角色。即使它在评论中指出问题已修复、CI 已通过，最终合并仍需要满足分支保护规则的要求——比如至少一人 approve、通过所有状态检查等。

Claude Approvals 则在策略文件允许的范围内自动批准。但策略文件本身只是附加信号，不是替代分支保护规则。如果你的仓库配置了「必须经人工审核才能合并」的保护规则，Claude Approvals 的自动批准也不会生效。



![分支保护规则兜底](https://iili.io/oqCrGKQ.png)
> 分支保护规则兜底



这两个机制构成了一层安全网：即使 Claude Ship 判断失误，分支保护规则仍然阻止了不符合团队规范的合并。

## 下一步会怎样

### Beta 阶段的判断、值得关注的变化

Claude Ship 目前处于 beta 阶段，Code Review 已正式可用，PR Steward 和 Claude Approvals 仍在测试。官方给出的内部数据是：Claude Code 团队 6 月至 9 月合并 PR 数量翻倍，回滚比例下降超过 40%。

这个数字值得关注，但也要理解其背景。测试团队本身就是 Claude Code 的重度使用者，他们的代码大部分由 AI 生成，代码质量基线可能高于平均水平。对于刚从传统开发模式迁移的团队，短期内可能面临更高的学习成本和试错成本。

更值得观察的是策略文件的演进。Claude Approvals 的审批逻辑完全由团队自写的策略文件驱动，可以用自然语言描述。审批规则本身也会成为团队知识的一部分，随着使用深入不断迭代。

Beta 阶段还有一个明显边界：Claude Ship 可能遗漏 bug、安全漏洞或其他问题。这不是理论风险，而是 Anthropic 在文档中明确列出的已知限制。AI 审查依赖上下文和训练数据，对代码库特定领域的隐性依赖关系、历史遗留问题，识别能力仍有限。

对团队而言，现在的合理策略是：在观察模式下运行 Claude Approvals，对比 AI 审批判断和人工判断的分歧点，逐步调整策略文件。等分歧率降至可接受水平后，再考虑放开自动批准。分支保护规则保持不动，作为最后的兜底。

一年前 Claude 能写完代码，一年后它开始接管 PR 流程。剩下的问题不是技术能不能做到，而是团队愿不愿意把信任交给这套系统，以及信任需要多少数据来换取。
